FOC Web -- outstanding work
===========================

Everything here is verified against the map, not speculative. Counts are
measured, not estimated.

EFFECTS (closing out the effects pass)
--------------------------------------
[x] Fractional alpha on geoset visibility  (FIXED)
    Geoset visibility was binary -- render.js did `mesh.visible = a > 0.05`.
    Warcraft III draws the geoset at the track's own alpha, so anything meant to
    fade popped instead. Now the alpha reaches the material, and it is
    multiplied into the authored opacity rather than replacing it, so a geoset
    animation and a SetUnitVertexColor compose (0.5 x 0.5 = 0.25) instead of the
    last writer winning.
    18 of the 1105 converted models carry an alpha strictly between clear and
    solid: the five auras, War Stomp's and Thunder Clap's caster rings, four
    missiles, the three feathers, green smoke, the goblin sapper and the sand
    wave. Trueshot Aura's ring is the plainest case -- authored to run
    0.30 -> 0.535 -> 0.30 and never solid at any point, so it had been drawn at
    full opacity for its entire life.
    A model that never fades still pays nothing: materials are only cloned when
    a geoset is actually part-way through one.
    Found while fixing it: two of the eighteen -- Devotion Aura and the Voodoo
    Aura -- have no glTF animation at all, because nothing on them moves and the
    geoset alpha *is* the animation. No clip meant no mixer, no mixer meant no
    time to sample, so they were frozen on their first frame, which for both is
    fully transparent. They now get a clock of their own from the sequence's
    duration. tools/geoset_test.mjs, 15 checks.

EFFECTS (cont.)
---------------
[ ] Buff art -- no buff ever shows its attached model
    Warcraft III gives a buff a Target Attachment model and an attachment point
    (w3h fields ftat / fta0). Nothing reads w3h, buffs are never serialised to
    the client, and no attach/detach path exists -- so no buff in the map has
    ever drawn its art. 19 models are referenced and all 19 are already
    converted, so this is wiring, not extraction.
    Visible example: Ichigo's Hollow form (B001) and Vizard form (B000) both
    attach Abilities\Spells\Undead\DeathCoil\DeathCoilMissile.mdl at "head".
    That missing orb is the unchanged-model half of the report.

Warcraft III's own screenshot still has and we do not:

[ ] The camera does not know the console takes 29% of the screen
    That height is the game's own number, but our view was built for a full
    window, so the world is squashed into what is left rather than framed for
    it. This is the one item with a gameplay cost, not just a visual one, and
    it is the reason to do it before the rest.

    ConsoleUI.fdf genuinely splits it across Tile03 and Tile04. This is the same
    seam that cuts the portrait arch in half, and seamArch() in console.js

    GOLD and K/D run out of the opening at 1440x900.

PERFORMANCE
-----------
[ ] Skinning is the suspected remaining cost, unconfirmed on real hardware
    On a 4080 at 307 units the frame is 45 ms while the GPU has only 137k
    triangles and 1559 draw calls to draw -- so it is CPU, not the card.
    Freezing animation saves 29 ms with the draw calls unchanged, and only 9 ms
    of that is measurable in our own timers; the rest is three.js recomputing
    and uploading a skeleton per visible skinned mesh during render. Confirm
    with the in-game keys before optimising: ` for the readout, [ to freeze
    animation, ] to hide units.
    Ruled out already: merging geosets to cut draw calls. Only 8% of them are
    safe to merge -- the rest share a material but not visibility, and merging
    those breaks the animated geoset switching that Bankai depends on.

[ ] GPU texture handles are never released, and disposing them does not help
    Geometry and materials now come back on removeView -- 29 -> 55 -> 29 over
    three spawn/remove cycles, asserted in render_test. Textures do not:
    renderer.info.memory.textures climbs 9 per unit spawned and never falls,
    for the whole match.
    It is not a reference we hold. At rest between cycles the scene traverses
    to 2 meshes and 2 textures, flat, and exactly 3 Texture objects are created
    per spawn -- the texanim layer clones, which releaseGPU does dispose.
    The mechanism is three.js's own accounting (r185, WebGLTextures):
    info.memory.textures counts one entry per (texture.source, sampler-state
    key), where the key is getTextureCacheKey -- wrap, filters, anisotropy,
    colorSpace and friends. An entry is only freed when its usedTimes reaches
    zero, so disposing one texture that shares an entry moves nothing:
    measured, disposing a texanim clone changes the counter by 0.
    What has NOT been established is which 9 that is, given only 3 objects are
    born. The next step is to instrument getTextureCacheKey rather than guess
    -- the signature (monotonic growth, nothing retained) is what you get when
    a shared texture's key changes after it has been uploaded, which orphans
    the old entry forever. Look for a per-spawn write to a cached texture's
    wrap/filter/colorSpace.
    Worth keeping in proportion: the pixel data is uploaded once per source and
    shared, so this is handle growth rather than image growth. It is still
    unbounded, and it is the last thing standing between the ` counters and
    actually flattening.

[ ] o00D has no entry in unittypes.json
    Portgas D. Ace's A05N names it as a morph form and the compiled table has
    no such unit, so it reaches the client with nothing to draw. ghost_test
    catches it. Predates the performance work. It no longer produces an
    invisible pickable unit -- spawnView falls through to the capsule stand-in
    now -- but a capsule is a placeholder, not the model, so the entry stays.
    This is the one test `npm test` reports as known-failing rather than as a
    failure; the fix is to delete its row in tools/run_tests.mjs once o00D has
    an entry, not to edit the test.

[x] tools/ghost_test.mjs prints raw format specifiers  (FIXED)
    Its console.log used %-6s and friends: Node's format understands %s and %d
    but none of printf's width flags, so the specifier printed itself and

SOUND
-----
[x] Warcraft III's own hero-death warning  (FIXED)
    "Our hero has fallen!" is the engine's, not the map's: nothing in
    war3map.j mentions it, which is why it had never been ported. UISounds.slk
    carries HeroDies<Race> for your own hero and AllyHeroDies<Race> for an
    ally's, all 11 rows already converted to ogg by the existing audio step.
    Three details that make it more than "play a sound on hero death": the
    voice is the *listening* player's race rather than the dead hero's, so the
    row is chosen per client and the server only reports the death; there is no
    enemy row in the table at all, so Warcraft III is silent when the other side
    loses one, and so are we; and it is not a 3D sound -- it plays at its own
    volume wherever the hero fell, because the voice is yours and not the
    battlefield's. 25 of the 26 heroes are race human and one is orc, so the
    race is read from unittypes rather than assumed.
    The rows also carry Flags, and every one of them is NODUPLICATES: Warcraft
    III will not start the warning while it is already playing, which in a map
    where heroes die constantly is the difference between a warning and a
    pile-up. Honoured. CHANNELFULLPREEMPT is deliberately not -- it decides what
    to evict when a mixer channel is full, and there is no channel model here.
    The premise was checked rather than assumed: mapmakers ask how to *remove*
    this sound, so it fires in custom maps by default, and FOC never suppresses
    it -- zero VolumeGroupSetVolume, zero SetSoundVolumeBJ, no VOLUME_GROUP_*
    anywhere in war3map.j. What is still unverified is the exact firing rule in
    a 10-player free-for-all; worth a listen in the real client.
    tools/warnsound_test.mjs, 15 checks, covering all four branches.

[ ] The rest of the UISounds warning family is still unported
    The same table drives TownAttack<Race>, AllyUnderAttack<Race> and a dozen
    others on the same pattern. Only the hero-death rows are compiled into
    data/uisounds.json so far. Nothing else is wired to fire them yet, so this
    is a "when there is something to warn about" item, not a gap in what plays.

SERVER
------
[x] Room lifecycle  (FIXED)
    Two bugs stacked. reset() kept players who had left during a match, so every
    finished match left its pair behind and after five the ten slots were gone.
    Then the fallback for a full room walked PLAYER_SLOTS, ran off the end, and
    used the loop *index* as the slot -- which at a full room is 10, itself a
    real slot on team 0 and already taken. Two late joiners both became player
    10 on team 0, and the duel they were meant to fight had one side empty.
    Now: reset() drops anyone with no socket, and a genuinely full room refuses
    the join instead of inventing a seat. tools/room_test.mjs drives twenty
    match cycles through one room and checks both.

    FIXED: he respawns, and the Hollow form grants its AGI x3 attack bonus.
    OPEN:  the buff's attached art -- see "Buff art" below.

FIXED -- metamorphosis (kept for the reasoning; delete once it has bedded in)
----------------------------------------------------------------------------
[x] An alternate form drew as the unit it transformed from
    Warcraft III has no native that changes a unit's model. A metamorphosis
    swaps the unit for another *type*, and where both types name one model file
    the difference is carried by Required Animation Names: the alternate type
    asks for "alternateex" and the model's geoset animations show a different
    body in its "... Alternate" sequences. Three things were in the way:
      - tools/unittypes.py never mapped 'uani', so a map that set the field
        itself lost it. O000 (Bankai) reached the client with an=null.
      - pickClip treated a unit's declared tokens as a tiebreak used only when
        nothing matched exactly, so a model carrying both "Stand" and "Stand
        Alternate" always drew the plain one. 57 unit/animation pairs across 22
        unit types were wrong: the Castle drew as a Town Hall, the Fortress as a
        Great Hall, the swimming penguin as a walking one, the Obsidian
        Destroyer as the statue, Illidan's demon form as Illidan.
      - "alternateex" names no sequence in any of the 1101 converted models
        while "alternate" names 214, and every unit type declaring it is the
        morphed form of another, so it asks for "alternate".
    Covered by tools/morph_test.mjs (needs FOC_DEBUG=1: Bankai is a level-10
    skill and the level-to-cap key is the only way there without playing).

[x] A metamorphosis left the form's own abilities behind
    world.morph swapped the stat block and nothing else, but the alternate type
    is where a transformation's power usually sits. Goku's three Super Saiyan
    forms are +50/+100/+150 to all attributes and granted none of it; Ichigo's
    Bankai carries the Black Getsuga. 16 forms are reachable through morph();
    none of them declares Locust, Invulnerable or Permanent Invisibility, so
    granting the list wholesale is safe. Hero abilities are deliberately not
    granted -- an alternate form declares the same ones so they carry across,
    and granting them would hand the player ranks they chose not to learn.

[x] Attribute skills did nothing until something else recalculated
    learnSkill changed u.abilities and never called recalc, so Attribute Bonus
    and its kin sat inert until the next level-up, item or buff happened to run
    one. Now every path that changes a unit's ability list recalculates.

[x] ATTR_SKILLS knew one of the 24 bases that can carry an attribute bonus
    AbilityMetaData.slk names them on the useSpecific column of Iagi/Istr/Iint.
    We had 'Aamk', so every transformation built on AIx2 granted nothing.
    Deriving the set from the data instead would have been wrong: AInv's data1
    is how many inventory slots it opens and AIcf's is a damage figure.

NETWORK
-------
[ ] No rejoin, only a reload
    A dropped socket now says so and offers a refresh, which is what the review
    asked for as a minimum. Actually rejoining means the server holding the slot
    for a moment rather than dropping the player on close, and the client
    replaying WELCOME and the next snapshot onto the world it already has. The
    room already knows how to evict a player with no socket, so the missing
    half is the grace period and the client-side re-attach.
